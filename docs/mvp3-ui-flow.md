# MVP 3 UI Flow

## User Journey Overview

The complete guided user journey for MVP 3 should feel like a lightweight wizard:

```text
Welcome
→ Number of Credit Cards
→ Credit Card Names
→ Credit Card Details
→ BNPL Plan Entry
→ Review
→ Generate Projection
→ Results
```

The exact implementation may use steps, tabs, or panels, but the user experience should feel like a guided, progressive workflow.

## Global Navigation Pattern

The UI should provide a clear, visible progress indicator that helps the user understand where they are in the flow.

Recommended navigation behavior:

- show a visible progress indicator, for example `Step 3 of 7` or a restrained labelled step sequence such as `Cards → Details → Plans → Review`
- provide `Back` and `Continue` actions
- keep one primary action per screen
- preserve entered data while navigating within the active session
- avoid data loss when moving between steps in the active session
- validate before advancing where appropriate
- entered data is temporary and may be cleared by refreshing the browser, restarting the application, or selecting `Start over`
- MVP 3 does not provide recovery or persistence after the session is cleared

Primary action labels should use friendly language such as:

- `Continue`
- `Add another plan`
- `Review my details`
- `Generate my projection`

Avoid generic labels such as:

- `Submit`
- `Execute`
- `Process`

## Screen 0: Welcome

### Purpose

Introduce the product and set expectations.

### Suggested Content

- product name
- short description: `See how your BNPL plans affect future credit-card statements and cash flow.`
- reassurance: `Your data stays in this local session and is not saved.`
- primary action: `Get started`

This screen should be visually simple and may be optional if implementation simplicity requires starting directly at Screen 1.

## Screen 1: Number of Credit Cards

### Prompt

`How many credit cards do you want to track?`

### Fields Collected

- positive integer number of cards

### Behavior

- minimum value: 1
- use a simple number input or stepper
- store the value in session state
- create the corresponding card placeholders

### Primary Action

`Continue`

## Screen 2: Credit Card Names

### Prompt

`What should we call your cards?`

### Fields Collected

For each card, collect:

- card display name

Examples:

- RBC Visa
- TD Cashback Visa
- Tangerine Mastercard

### Behavior

- display one clear input per card
- require non-empty names
- preserve entered names when navigating backward
- generate stable internal card IDs automatically
- internal IDs should not be shown to the user
- internal IDs are generated by the UI and are never manually entered
- renaming a card must not break BNPL-plan references because the payload continues to reference the stable internal card ID
- implementation details for generating IDs belong in the implementation plan, not this flow document

### Primary Action

`Continue`

## Screen 3: Credit Card Details

### Prompt

`Add the statement details for each card.`

### Fields Collected

For each card, display a card-based panel containing:

- card name
- statement closing day
- payment due day
- current or existing balance

### Field Requirements

#### Statement Closing Day

- integer day of the month from 1 to 31
- not a complete calendar date
- user-facing label: `Statement closes on`

#### Payment Due Day

- integer day of the month from 1 to 31
- not a complete calendar date
- user-facing label: `Payment is due on`

#### Existing Balance

- monetary input
- default: `0.00`
- zero or positive
- user-facing label: `Current card balance`

### Behavior

- one visual card per credit card
- avoid dense table-style entry
- show concise helper text where useful
- preserve values in session state

### Primary Action

`Continue`

## Screen 4: BNPL Plan Entry

### Prompt

`Now add your BNPL plans.`

The screen should immediately show at least one editable BNPL plan row or card.

Do not require a separate introduction-only screen.

### Fields Collected

Each plan should collect:

- provider name
- plan name
- purchase amount
- currency
- purchase date
- first installment date
- installment count
- installment frequency
- credit card

### Field Details

#### Provider Name

User-facing label:

`Provider`

Examples:

- PayPal
- Klarna
- Afterpay

#### Plan Name

User-facing label:

`What did you buy?`

Examples:

- Radar
- Epic Games
- Bike Helmet

#### Purchase Amount

User-facing label:

`Total purchase amount`

- monetary value
- must be greater than zero

#### Currency

- dropdown
- supported values: `CAD`
- `USD`
- supported currencies are defined by the approved MVP 2 JSON contract
- the UI must not introduce additional currencies
- the UI must pass the selected contract value to the backend without conversion
- the UI must not perform currency conversion or exchange-rate calculations

#### Purchase Date

User-facing label:

`Purchase date`

#### First Installment Date

User-facing label:

`First payment date`

- may default to the purchase date as a UI convenience only
- the user remains responsible for reviewing and confirming the value
- the UI does not infer the provider's actual payment schedule
- backend validation remains authoritative

#### Installment Count

User-facing label:

`Number of installments`

- positive integer

#### Installment Frequency

- dropdown
- supported MVP 3 value: `BIWEEKLY`

The user may see a friendlier label such as:

`Every 2 weeks`

The payload must still use `BIWEEKLY`.

#### Credit Card

User-facing label:

`Credit card`

- dropdown populated from cards entered earlier
- display the human-readable card name
- store the selected stable internal card ID in the payload
- the payload must reference the stable internal card ID, not the editable display name

## Add and Remove Plan Behavior

The user must be able to:

- add another BNPL plan
- remove a BNPL plan
- edit any existing plan before submission

Use friendly controls:

- `+ Add another plan`
- `Remove plan`

### Rules

- at least one BNPL plan must remain
- removing a row should not affect other rows
- internal plan IDs should be generated automatically
- plan IDs should not be shown to the user

### Primary Action

`Review my details`

## Screen 5: Review

### Purpose

Allow the user to verify all information before calculation.

### Display Content

#### Credit Cards

For each card:

- card name
- statement closing day
- payment due day
- existing balance

#### BNPL Plans

For each plan:

- provider
- plan name
- purchase amount
- currency
- purchase date
- first installment date
- installment count
- frequency
- selected credit card

### Behavior

- show information in readable summary cards
- provide an `Edit` action that returns to the relevant step
- do not calculate anything yet

### Primary Action

`Generate my projection`

## Submission Behavior

When the user selects `Generate my projection`:

1. Build the existing MVP 2 JSON-compatible payload.
2. Pass it through the existing input validation layer.
3. Pass validated input through the existing application service.
4. Receive report-ready results.
5. Display the results screen.

The UI must not call individual rules functions directly.

## Validation Experience

Validation should be friendly and actionable.

The UI should:

- show errors near the relevant field where practical
- preserve all entered data after validation failure
- summarize multiple backend validation errors clearly
- avoid exposing internal field names when a friendlier label exists
- avoid technical wording and stack traces

Example:

Instead of:

`bnpl_plans[0].purchase_amount invalid Decimal`

Prefer:

`Enter a valid purchase amount for Radar.`

The backend remains authoritative for final validation.

## Screen 6: Results

The results screen renders the report-ready output produced by the approved MVP 2 backend.

The UI may improve typography, spacing, grouping, headings, responsiveness, and visual hierarchy, but it must not create new financial groupings, totals, projections, reconciliations, or report sections.

The UI must not independently derive statement impacts, projected balances, cash-flow obligations, or installment schedules.

Any displayed result section must already be supported by the approved backend reporting output. For example, the UI may present backend-supported sections such as `Installment Projections` or `Cash Flow Obligations`, together with any existing card-balance information already returned by the backend.

## Results Screen Actions

Provide:

- `Start over`
- `Edit my details`

### Behavior

- `Edit my details` returns to the review or relevant input step while preserving state
- `Start over` clears the active session state after confirmation

Do not add export, persistence, sharing, or account features in MVP 3.

## Empty and Edge States

Document behavior for:

- no generated result yet
- backend validation failure
- unexpected runtime failure
- user removes plans until one remains
- navigation backward and forward
- session reset

Unexpected failures should display a safe generic message such as:

`Something went wrong while generating your projection. Please review your details and try again.`

Do not display internal stack traces to normal users.

## Responsive and Accessibility Considerations

The flow should:

- remain usable on common laptop screen sizes
- use readable labels and font sizes
- maintain sufficient contrast
- avoid relying on color alone
- support keyboard navigation where Streamlit permits
- use clear focus and navigation order

MVP 3 is not required to be a mobile application, but layouts should avoid unnecessary horizontal density.

## Out of Scope

The flow must not introduce:

- authentication
- saved profiles
- persistence
- import/export
- editing historical plans
- payment tracking
- notifications
- bank integrations
- APIs
- cloud deployment
- new financial calculations

## Acceptance Criteria

The document must clearly define:

- the complete guided user journey
- every screen and its purpose
- every field collected
- Back and Continue navigation
- add/remove BNPL plan behavior
- review-before-submit behavior
- backend submission flow
- friendly validation presentation
- the results information hierarchy
- session reset and edit behavior
- no duplication of backend rules or validation
